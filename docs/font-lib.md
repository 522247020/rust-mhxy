# 点阵字库（原型）

大漠插件那种「字库」思路的 Rust 实现，用来替代 / 校验 OCR 对**坐标数字**的识别。
分支：`feat/ocr-font-lib`，代码：`src/font_lib.rs`（库）+ `src/bin/font_tool.rs`（工具）。

## 为什么是闭集匹配

坐标数字只有 12 类（`0-9`、`,`、`.`），地图名只有几十个。闭集只需要 argmax，
不需要绝对精度，所以在小字号、低对比度、抗锯齿下比通用 OCR 稳得多；代价是
必须**建库**，字体/DPI 变了要重建。

## 流程

```
RGB → 灰度 → Otsu 二值化（黑字白底）
     → 竖直投影切字（列空隙 ≤ gap_merge 视为同一个字）
     → 用「整行行高」统一裁剪每个字（不是各字墨迹外框，否则逗号/句点会归一化成同一个墨团）
     → 缩放到固定 cell（默认 16x24）
     → zNCC 打分，±shift 像素平移取最优
     → argmax + margin 判定；分数不够高时尝试从中间劈开（粘连字）
```

建库和识别共用同一套切字 / 归一化代码，所以字模和运行时输入同分布。

## 用法

### 0. 先把识别区域对上（位置不对时）

```bash
# 看游戏窗口的客户区坐标
cargo run --bin font-tool -- windows

# 整屏截图 + 拖拽框选：自动算出相对客户区的百分比，并当场拍一张校验图
cargo run --bin font-tool -- pick --write-config
#   Enter 确认、Esc 取消；--write-config 会把结果写回 config.json
#   （ocr/task_region + 当前分辨率的 region_presets）
```

`pick` 会做三件事：

1. 从拖拽的屏幕坐标反算相对客户区的百分比（自动选「与选区重叠最多」的窗口，
   不依赖窗口枚举顺序）；
2. 检查选区中心是不是被别的窗口盖住（盖住了会提醒）；
3. 按算出的区域真截一张图，和框选画面比平均像素差——一致才算调对。

> **屏幕缩放**：`font-tool` 启动时会把自己设成 per-monitor-v2 DPI 感知，
> 和主程序（egui/winit）一致。否则系统开 125%/150% 时两边的客户区尺寸会差一个
> 缩放倍数（比如 809x632 对 1213x948），区域和 `region_presets` 全对不上。
> `windows` 命令首行会打印 `屏幕 / 系统缩放 / DPI 感知`，先看它。

不开界面直接写区域：

```bash
cargo run --bin font-tool -- region --region 0.795,0.292,0.985,0.538 --size 1218x994
cargo run --bin font-tool -- region --region 0.795,0.292,0.985,0.538 --dry-run  # 只打印
```

只需要单张截图（不跑 OCR）时用：

```bash
cargo run --bin font-tool -- snap --out target/panel.png            # 当前区域
cargo run --bin font-tool -- snap --desktop --out target/desktop.png # 整屏
cargo run --bin font-tool -- crop --image target/desktop.png --crop 931,739,812,663 --out x.png
```

### 1. 自动采集（推荐）

不用裁剪、不用手打标注：工具自己截当前游戏窗口、跑本地 PP-OCR 拿文字、
按检测框切成字模、把 OCR 文字当标签，多帧**聚类 + 投票**后直接写字库。

```bash
# 先看一眼区域对不对（只截图，不跑 OCR）
cargo run --bin font-tool -- snap --out target/panel.png

# 采集 20 帧，直接产出字库
cargo run --bin font-tool -- capture --out assets/fontlib.json --frames 20 --interval 800
```

窗口、区域、预处理、放大倍数默认取 `config.json` 里的现有设置（包括按分辨率
保存的 `ocr/region_presets`），也可以用参数覆盖：

```bash
cargo run --bin font-tool -- capture --out assets/fontlib.json \
  --window 梦幻西游 --region 0.70,0.24,0.99,0.70 \
  --preprocess color,binary --color #eaff65 --tolerance 24 --upscale 2
```

采集时每个字模样本都会投票：

- 按外观聚类（相似度 ≥ `--min-similarity`，默认 0.9）——同字体同抗锯齿的字模几乎一样；
- 同一个簇内对标签投票，平票保持原判，只有**严格多数**才改判；
- OCR 认错的单帧会被压掉；如果一整个簇多数票都是错的，说明 OCR 在这一段系统性
  认错，会用「提醒」打出来，让你判断要不要重建。

默认只学数字和分隔符（`0-9`、`,，、.．。`），避免把界面上的中文和噪声塞进坐标字库；
`--all` 连中文一起学（做地图名字库时才需要）。

参数：`--frames` 帧数、`--interval` 间隔毫秒、`--cell 16x24`、`--dump <目录>`
（把每帧面板和各检测框的裁剪图存下来，方便排查采错）、`--min-similarity`、
`--padding`（裁剪框外扩像素，默认 2，和运行时复核一致）。

输出示例：

```
窗口：梦幻西游（客户区 Some((812, 663))）｜区域 (0.795, 0.292, 0.985, 0.538)（来自 config.json 的 ocr/task_region）｜预处理 关闭｜放大 2x｜20 帧，间隔 800 ms
第 1/20 帧：面板 308x326，采到 12 个字模｜OCR 抓鬼 长寿村 79,26 附近 / 鬼王 天宫 12,45
...
已写入 assets/fontlib.json（16x24，12 个字模，164 个样本，来自 18/20 帧）
,×1（12 票）  .×1（6 票）  0×1（14 票）  ...
```

### 2. 手动准备样本（可选）

如果自动采集的标签不可信，也可以给准确标注：

```
samples/
  line1.png   # 一行文字截图（原始截图或已二值化都行）
  line1.txt   # 这行的准确文字，例如：79,26
  line2.png
  line2.txt
```

```bash
cargo run --bin font-tool -- build --samples samples --out fontlib.json
```

输出里会列出每个字的样本数。切出来的字数与 `.txt` 字数不一致的样本会被跳过并
打警告（通常是截图裁掉了字）。

### 3. 在截图上读字

```bash
# 整块面板：先按行切分
cargo run --bin font-tool -- read --lib fontlib.json --image panel.png

# 整张图就是一行
cargo run --bin font-tool -- read --lib fontlib.json --image line.png --line

# 从截图里裁一块再看，顺便把二值化结果 dump 出来核对切字
cargo run --bin font-tool -- read --lib fontlib.json --image shot.png \
  --crop 200,300,260,80 --save-binary target/debug-binary.png
```

每行输出 `y=<行顶> <识别文本> [不可信] 每个字(label/分数/margin)`。

### 4. 真实截图冒烟测试

```bash
MHXY_FONT_SAMPLES=samples MHXY_FONT_IMAGE=panel.png \
  cargo test --bin font-tool reads_real_screenshot -- --ignored --nocapture
```

支持 `MHXY_FONT_CROP=x,y,w,h`。

## 参数（`MatchConfig`）

| 字段 | 默认 | 作用 |
|---|---|---|
| `min_ink` | 1 | 一列至少多少黑像素算笔画 |
| `gap_merge` | 1 | 列空隙 ≤ 该值并成同一个字 |
| `split_when_below` | 0.95 | 分数低于该值才尝试劈开 |
| `split_gain` | 0.05 | 两半都要比整块高这么多分才接受拆分 |
| `max_split_depth` | 3 | 递归拆分深度上限 |
| `min_split_width` | 4 | 窄于该像素数的字不尝试拆分 |
| `shift` | 2 | 匹配允许的 ±像素平移 |
| `min_score` | 0.5 | 低于该分数判不可信 |
| `min_margin` | 0.05 | 与次优 label 的差值过低判不可信（形近字） |
| `row_gap` | 2 | 行切分的空隙容差 |

## 接入 OCR 流程

主程序里已经接上，开关默认关：侧边栏「识别方式」卡片 →「点阵字库复核坐标」。
对应配置：

```json5
"ocr/font_lib": true,
"ocr/font_lib_path": "fontlib.json",  // 留空 = assets/fontlib.json，相对路径相对 assets
```

流程（`src/coord_fix.rs`）：

```
OCR 返回「文本 + 每个检测框的坐标 / 置信度 / 字符区间」
  → 在框内文本里找坐标形状 d{1,3}[,，、.。]d{1,3}
  → 按框坐标从「送 OCR 的那张图」里裁图（外扑 2px），字库重读
  → 只接受：字库高置信 且 整块刚好就是一个坐标 且 字数与 OCR 框内一致
  → 用字符区间就地替换文本里的坐标，其余文字一个字都不动
  → 文本继续走 parse_tasks + 地图边界校验
```

几个细节：

- 只对**本地识别**生效：远端接口只回纯文本，没有检测框，无法定位要复核哪一块。
- OCR 把数字认成字母（`6→G`、`0→O`、`1→l`）时，替换区间会吞掉这些字母，但不会吞中文
  和全角标点，所以「坐标（79,26）附近」这种结构不会被拆错。
- 字库推翻 OCR 时会在详细日志里留一行 `字库复核坐标 79,2G → 79,26`，方便核对
  是字库救回来了还是字库改坏了。
- 每一帧都会额外记一行带成功率：

  ```
  字库复核：坐标段 1｜确认 1（成功率 100%）｜一致 0｜改写 1（改写率 100%）｜无法确认 0
  ```

  没有坐标时是「本帧没有坐标形状的文字，字库未参与」。
- 侧边栏开关下方有累计统计（含成功率）：

  ```
  累计：38 帧｜坐标段 12｜确认 11（成功率 92%）
  　　　一致 6（55%）｜改写 5（改写率 45%）
  上一帧：坐标段 1｜确认 1（成功率 100%）｜一致 0｜改写 1（改写率 100%）｜无法确认 0
  ```

  怎么读：
  - **成功率**（确认/坐标段）= 字库敢下结论的比例。低 → 字模不全、放大倍数不对、预处理没把字切干净；
  - **一致**（字库读出与 OCR 相同）= OCR 本来就对，字库只是复核一遍；
  - **改写率**（改写/确认）= 字库真正动手的比例，也就是「帮上了多少忙」；
  - **无法确认**（坐标段 − 确认）= 字库宁可不改的那些（分数/margin 不够、字数对不上）。

  所以「提升效率」可以直接看两个数：`改写率`（动手比例）和
  `一致率`（不改写的时候是不是因为本来就对）。如果 `一致` 接近 100%、`改写` 接近 0，
  说明 OCR 在这块面板已经足够好，字库主要是安全网。
  - `F`（帧）不涨 → 根本没跑识别（或走的远端模式）；
  - `F` 涨、`C = 0` → 跑过了，但画面没有带坐标的任务行（调区域/任务类型）；
  - `C > 0`、`M = 0` → 字库参与了但不够确信（典型是放大倍数/字体不对，或字模不全）。

> 注意：这里的「成功率」是**字库与 OCR 的一致程度**，不是绝对准确率（没有人工真值）。
> 要看绝对准确率，用 `font-pick` 的「验证 + 期望文本」，或 `font-tool verify` 的对比数字。
- 字库读不确信（分数 / margin 不够、形状对不上、字数对不上）就**完全不改**，行为退回改造前。
- 「取点窗口 → 测试 OCR」故意不复核，看到的永远是 OCR 原文，便于分清是谁认错了。

## 已知限制

- 字体/字号/DPI 变化大时要重建库；`cell` 尺寸固定，极端长宽比会失真。
- 形近字（`0/O`、`1/l`、`8/B`）靠 `margin` 暴露风险，不保证分辨。
- 纯色块（空白、全黑）zNCC 无意义，直接判 0 分并标记不可信。
- 目前只做「认数字」：建库用数字/标点样本即可；地图名仍靠 OCR + 模糊匹配。

## 采集后怎么判断够用

```bash
cargo run --bin font-tool -- info --lib assets/fontlib.json
```

```
assets/fontlib.json：16x24，24 个字模
0×3  1×7  2×8  5×1  7×5
提醒：还缺这些坐标字符：34689,.
```

**必须覆盖 `0-9` 和 `,` `.`**，缺一个就意味着含该数字的坐标永远判「不可信」→
不替换，等于没生效。缺字符通常是因为采集时任务栏里没有带坐标的任务：
抓鬼/鬼王/降妖这类「去 XX（79,26）附近」的任务行才会贡献数字。

采集会**自动合并**到同一份字库（`--fresh` 才从零重建），所以可以边做任务边跑，
分几次把 12 个字符补全。每次都会打印缺什么。

## font-studio：图形界面采集（自动）

命令行那套要背参数、看不到画面。`font-studio` 把同一个流程摊开成一个窗口：

```bash
cargo run --bin font-studio
```

（也可以 `cargo build --release` 后直接双击 `target/release/font-studio.exe`。）

界面分四块：

| 区域 | 作用 |
|---|---|
| 顶栏 | 「刷新窗口」+ 窗口下拉（只列标题含「梦幻西游」的窗口）+ 屏幕缩放/DPI 提示 |
| 左侧「识别区域」 | 「框选区域」在整屏截图上拖框，自动换算成相对客户区的百分比；也可以直接改文本框；「写回 config.json」= 主程序取点 |
| 左侧「预处理」 | 颜色提取 / 灰度 / 二值化 / 反色、文字颜色与容差、放大倍数、高召回；「截图预览」立即抓一张看效果 |
| 左侧「采集」 | 帧数、间隔、聚类相似度、「连中文一起学」、是否合并已有字库；采集进度与耗时 |
| 左侧「字库」 | 路径、「读取 / 保存 / 清空」、字模数与覆盖报告（缺哪个坐标字符直接标红） |
| 中间 | 预览图（就是送 OCR 的那张）+ OCR 文本 + **切出来的字模条**（检查切字有没有粘连/切坏） |
| 下方「字库字模」 | 每个学到的字模（16x24）一个格子：点一下可**改标签**或**删除**——OCR 标错的样本这样清掉 |
| 底部 | 日志：每帧学到多少、OCR 原文、采集汇总、冲突提醒 |

推荐顺序：**刷新窗口 → 框选区域 → 截图预览（确认画面和切字）→ 开始采集 →
看覆盖报告缺什么 → 做一轮带坐标的任务再采集（会自动合并）→ 保存**。

覆盖齐了（`0-9` 和 `,` `.`）再去主程序勾「点阵字库复核坐标」。

### 后台积累模式（边玩边攒）

左侧「采集」里除了固定帧数采集，还有「**后台积累**」：

- 不设终点，按「间隔 ms」一直抓；**窗口最小化/被盖住**只会跳过那一轮并记日志，不会退出；
- 画面没变化（对着同一个界面发呆）会按面板指纹跳过，不浪费 CPU；
- 每轮把最新字库回传给界面：字模网格、覆盖报告实时变，日志逐轮汇报；
- 一旦 `0-9` 和 `,` `.` 齐全，会打一条 **「覆盖齐了」** 并在按钮下方标绿 —— 这时停下来点「保存」；
- 积累过程中字模**不能改标签/删除**（每轮会被回传覆盖），要改就先「停止积累」。

典型用法：开着它去做抓鬼/鬼王，回来看到「覆盖齐了」→ 停止 → 保存 → 去主程序勾「点阵字库复核坐标」。

### 预处理很关键：背景没清掉，切字就会错

游戏任务栏背景是渐变的，文字是彩色的。如果**不勾「颜色提取」**，
`binarize` 会把背景的纹理也当成笔画，列投影把相邻字粘成一大块 —— 这时
「切出 N 个字模」和文字字数对不上，或者对上了但每个格子其实横跨两三个字。

正确的做法（`font-studio` 里）：

1. 勾「**颜色提取**」+「二值化」；
2. **在预览图上点一下任务文字**，自动取到颜色并填进「文字颜色」；
3. 勾「**显示二值化**」看效果：应该只剩文字、背景全白；
4. 容差从 20 左右微调，直到切出来的字模**一格一个字**；
5. 再去采集。

标签对齐现在是「按字宽动态规划」：中文 1.0、数字 0.55、逗号 0.35 个字宽，
把 OCR 的一行文字对上切出来的跨度，合并跨度（`119,60` 这种）会按比例再切开。
对齐误差超过 50% 的跨度**整段跳过**（说明切字是坏的），不会写进字库。

排查工具：

```bash
# 看一段文字怎么对齐到切出来的跨度
cargo run --bin font-tool -- align --image crop.png --text "朱紫国119,60处抓酉时"

# 把字库渲染成对照图，肉眼查标签
cargo run --bin font-tool -- sheet --lib assets/fontlib.json --out target/sheet.png
```

## font-pick：完全手动圈字（不跑 OCR）

自动采集和「点选建库」都依赖 OCR 的检测框与切字；中文混排时框一错、切字一错，
标签就跟着错。`font-pick` 是最后一道兜底：**不识别、不切字**，只做「你圈一个字、
你填这个字」这一件事。

```bash
# 可以带一张已有截图启动（也可以不带，进去再抓窗口）
cargo run --bin font-pick -- target/panel.png
```

流程：

1. 「抓游戏窗口」截整个客户区（或「抓整屏」/「打开图片」）；
2. 视图选「原图」，切到「取色」，**点一下任务栏里的文字**——自动勾上颜色提取、
   把容差调到能看出笔画，并切到「二值」视图；
3. 点下方 `0-9 , .` 选当前标签（也可以直接按键盘数字键），然后在图上**拖框**
   圈住一个字，松手就加入字库；
4. 有两种标签方式：
   - **整行文字**（推荐）：把这一行的字一次填进去，比如 `119,60`，然后从左到右
     每个字拖一个框，标签会自动按顺序取；`Ctrl+Z` 撤销时进度也一起退回去；
   - **当前标签**：点 `0-9 , .` 或按键盘数字键选一个字，之后每个框都用它
     （点标签/改标签框会自动切回这种模式）。
5. 下方「字模」格子显示最终 16x24 的样本，点一下可改标签或删除；
   `Ctrl+Z` 撤销上一步，`Ctrl+S` 保存，`Delete` 删除选中；
6. 覆盖报告不红了（`0-9` + 分隔符齐）→「保存」。保存前会把旧文件备份成
   `fontlib.json.bak`。

几个关键点：

- **吸附墨迹**（默认开）：取「大部分落在框里」的连通块的并集外接矩形。
  框画松了不会把背景噪点算进去；框画小了一点，笔画伸出去的部分也会被带回来；
  隔壁字只被框到一角时（大部分在框外）不会被误并。画完可以看框和缩略图确认。
- **不吸附**：字模严格等于手画的框，适合你已经量准了的情况。
- 视图里的「原图 / 预处理 / 二值」切换只影响显示，画框坐标三张图完全一致。
- **放大倍数要和主程序一致**（左侧「放大」默认 2x，对应 `config.json` 里的
  `ocr/upscale`）。运行时是 2x 截图后取字模，手动画也要 2x，否则字的抗锯齿
  不一样，分数会明显下降。改了放大倍数后当前图会重新铺满，旧框只影响显示。
- 滚轮以鼠标为中心缩放，中键随时平移；「适应窗口」重新铺满。
- 字库用和运行时**同一套** `cell_of` 归一化，所以手动样本和自动识别同分布
  （单测 `manual_components_build_a_library_that_reads_the_line` 守住这条）。
- **体检**：每个字模拿去和「不含它自己」的字库比，最像别的字（分数 ≥ 0.4）的
  样本会标红、列在「可疑样本」里，点编号可选中删除重画。它不需要截图，
  专门抓「把 4 画成了 1」「样本是碎片」这类错。
- **验证**：用当前字库在当前截图上跑运行时的窄字形读取，日志里逐字打出
  `标签@分数/margin`；填了「期望文本」（如 `151,12`）会直接对比是否一致。
  没填就只看读出什么，适合确认预处理有没有把字切碎。
  注意同一张图建的库再验证同一张图会偏乐观，最好换一帧再测。

### 地图文字采集（单独的字库）

字库区顶部的「采集对象」可以切到 **地图文字**。地图名是中文、长度不一，
跟坐标数字不能用同一套模板。地图文字有两种**标注粒度**（默认单个字）：

| 粒度 | 库文件 | cell | 怎么标 |
|---|---|---|---|
| 整个地名 | `assets/mapfontlib.json` | 64x24 | 「地图名」选好地名，框住整个地名拖一下 |
| 单个字 | `assets/mapcharlib.json` | 24x24 | 「地名」填整条名字，从左到右每个字拖一个框 |

逐字模式的操作：

1. 「标注粒度」选 **单个字**；
2. 「地名」下拉选 `长寿村`（或手输）；
3. 在截图上从左到右每个字拖一个框，标签自动按「长 → 寿 → 村」前进；
4. `Ctrl+Z` 会把样本和字的进度一起退回去；「重来」重新从第一个字开始；
5. 「体检」检查是否有字模被标成别的字；保存到 `mapcharlib.json`。

逐字模式会用 `assets/maps` 里所有地名算出**地图字覆盖**：

```
地图字覆盖：63/128
还缺 65 个字：...
```

覆盖到 100%（或至少把任务里常见地名的字补齐）后，这套单字模板就能拿去做
地名闭集匹配。

其他规则：

- 地图库**不混进坐标库**：坐标识别只读 `fontlib.json`，不会被中文模板干扰；
- 「体检」同样适用：会把“某个字/地名最像另一个”的样本标红/列出；
- 「验证」暂不适用于地图 / 任务类型库——运行时的中文识别还没接，先把数据采齐；
- 切换采集对象/标注粒度前要先保存/清空当前库（有未保存改动时工具会拦住）。

### 任务类型库（抓鬼 / 鬼王）

任务栏顶部那两个字（抓鬼、鬼王）是**闭集**，也可以单独采：

- 「采集对象」→ **任务类型**，库文件 `assets/tasklib.json`，cell 40x24；
- 标签只有两个：点「抓鬼」或「鬼王」，然后框住整个词（两个彩色字）拖一下；
- 一个框一条样本，同一类型可以多框几帧；
- 界面会提示还缺哪个类型（`还缺：鬼王`）；「体检」可查出画歪的样本。

## 混排中文时怎么认坐标（窄字形策略）

任务栏的一行是「去长寿村（79,26）附近」这种中文+数字混排，而且 PP-OCR 会把
整行当成一个检测框、中文还常常认错。靠「文字第 N 个字 ↔ 第 N 个格子」对齐是
不可靠的，所以改成看**字形宽度**：

- 一行里中文近似方框（宽 ≈ 行高），数字只有一半宽；
- 只挑「宽度 ≤ 最宽组 72%」的组（整行都是数字时全部保留）；
- 再按相邻组的**起点间距**把窄组切成若干段（同一段数字的字距稳定，隔开的数字会断开）；
- 每段拼成字符串，用 `d{1,3}[,.]d{1,3}` 的形状校验。

建库和运行时复核用的是同一套：

| 环节 | 做法 |
|---|---|
| 建库 | 只给「窄组段」打 OCR 坐标子串的标签，中文一律跳过 |
| 复核 | 只读窄组段，读出坐标形状的串就替换掉 OCR 里的坐标，中文完全不参与 |

好处：中文认得对不对都不影响；也不再要求「整个 OCR 框正好是一个坐标」。

`font-studio` 预览里会直接显示 **「字库只认窄字形读出：「119,60」」**——空的话
说明当前面板/预处理下读不出来，先调预处理再采集。

## 点选建库（标签 100% 正确的做法）

自动打标签在这块面板上不可靠（OCR 把坐标和中文混在一个框、中文误识严重）。
`font-studio` 提供「点选建库」，完全绕开推断：

> 如果连自动切出来的格子都不可信（框横跨几个字、粘连、漏字），别在这里硬修 ——
> 用上面的 **`font-pick`** 自己拖框，不依赖任何自动切字。

1. 「截图预览」会跑一次 OCR，**按行画出检测框**，再在行内把文字切成格子；
2. 预览的鼠标模式选「**标字（建库）**」；
3. **点一个格子 → 回车**：标签用 OCR 的字符预填（多半是对的），错了改一下再回车；
4. 标签框保留上次输入：连着标同一个字的多种写法时，点格子 → 回车即可；
5. 「字库」区会提示 `还缺 0234`，缺哪个就等游戏里出现那个数字再标；
6. 齐了点「保存」。

> 建库前先「清空」（或 `--fresh`）：旧的错标签留着会继续污染读数。

### 切字规则（为什么行内能一刀切准）

游戏字体的排版规律：

- **2 个数字 = 1 个汉字宽**（半角字符都按半个汉字算）；
- **全角符号（`，` `（` `）` `：`）算 1 个汉字宽**；
- 坐标是 1~3 位数字，所以**每行长度不一样** —— 切分按「这一行自己的文字」
  等比例算，不去假设各行等长；
- 边界会尽量吸附到「没有墨迹的列」，避免把笔画切一半。

所以只要 OCR 把这一行的文字读出来，格子就是按真实字数切开的。

## 验收：字库自测

```bash
cargo run --bin font-tool -- verify --lib assets/fontlib.json --frames 6
```

它逐帧对比「字库只认窄字形读出的坐标」和「OCR 认出的坐标」：

```
合计：坐标段 6 个，字库读出 6 个，与 OCR 一致 6 个（100%）
```

- 一致率接近 100% → 可以打开主程序的「点阵字库复核坐标」；
- 明显偏低 → 别开（次品字库可能把对的坐标改错；代码里有「长度必须一致」的护栏，
  但错误替换依然可能发生）。

运行时复核现在的行为：同一个 OCR 框里，先试「整框即坐标」，不行再「只认窄字形」，
读出的坐标**长度必须与 OCR 那一段一致**才替换 —— 只修「认错一位」，不改结构。
